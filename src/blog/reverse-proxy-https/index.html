One Address, Many Services: Reverse Proxies and HTTPS

How blog.example.com and dev.example.com end up on the same server, why certificates renew themselves, and where to put the login in front of internal tools.

You have one server and one public IP address, but several things to run on it: a blog, an internal editor, a dashboard, maybe a photo library. All of them want to be reachable under their own name and all of them should use HTTPS. Opening a different port for each is clumsy and insecure. If your provider shares that address with other customers, read about CGNAT first.

The good news: one small piece of software solves all of this at once. It is called a reverse proxy.

What a Reverse Proxy Does

A reverse proxy is the receptionist of your server. Every request from the internet arrives at it first, on the standard ports 80 and 443. It looks at which name was requested and passes the request on to the right service behind it:

  • blog.example.com → the blog, running on port 3000 internally
  • dev.example.com → the editor and other tools, on other internal ports
  • anything unknown → rejected

The services themselves are never directly reachable from the internet. Only the proxy is.

HTTPS Without the Hassle

HTTPS needs a certificate that proves the server really is blog.example.com. Not long ago, certificates were bought, installed by hand and forgotten until they expired. Today the free certificate authority Let's Encrypt and the ACME protocol automate everything:

  1. The proxy asks for a certificate for a name.
  2. Let's Encrypt checks that you control that name, either by fetching a file from your server (HTTP challenge) or by looking for a DNS record you set (DNS challenge, required for wildcard certificates like *.example.com).
  3. The certificate is issued and renewed automatically well before it expires. A certificate check catches the rare case where renewal fails.

Certificate lifetimes are getting shorter across the industry, which makes automation not just convenient but necessary.

Popular Reverse Proxies

Tool Strength Verdict
Caddy HTTPS fully automatic, very short configuration The easiest start for small setups
Traefik Configures itself from container labels Great when everything runs in Docker
Nginx Proxy Manager Web interface on top of Nginx Good if you prefer clicking to configuration files
Nginx, HAProxy Extremely capable and fast For larger or special setups

A complete Caddy configuration for two sites can be this short:

blog.example.com {
    reverse_proxy localhost:3000
}

dev.example.com {
    reverse_proxy localhost:3100
}

The Login in Front of Internal Tools

Admin panels and editors should never be openly reachable. A reverse proxy can put a login in front of them, before a single request reaches the tool:

  • Basic authentication: a simple username and password at the proxy. Easy, but without two‑factor.
  • Forward authentication with a single sign‑on service such as Authelia or Authentik: one login page with two‑factor authentication protecting all internal tools.
  • Access only through a VPN: the internal names are not published at all and are only reachable for connected devices, see reaching your network safely.

This is exactly the pattern for a setup like a public blog. with an internal dev. next to it: the blog is open to everyone, the tools sit behind the proxy's login.

Details Worth Getting Right

  • DNS first: each name needs a DNS record pointing to your server before a certificate can be issued (DNS explained).
  • Pass on the real visitor address. Behind a proxy, every request seems to come from the proxy itself. Configure the proxy to send the original address in a header, and the application to trust it only from the proxy.
  • Redirect HTTP to HTTPS and send security headers such as HSTS. Most proxies do this by default or with one line.
  • Keep the proxy updated. It is the one component directly exposed to the internet.

Conclusion

A reverse proxy lets one server host many services under their own names, handles HTTPS certificates automatically and is the right place for a login in front of internal tools. Start with Caddy for a small setup, point DNS records at the server, keep admin tools behind authentication or a VPN, and let the proxy be the only thing the internet ever talks to.
